Chapter 7 — Strings and Common Functions

Text is the most common thing a program touches: names, file contents, log lines, form input, CSV rows. This chapter gives you the string skills you will reach for every day — pulling pieces out of text, cleaning it, splitting it apart and joining it back together, lining numbers up with f-strings, and building large strings without making the program slow.

Indexing and slicing

A string is a sequence of characters, so it supports the same indexing and slicing syntax as a list. Index 0 is the first character and negative indices count back from the end. A slice takes [start:stop:step], includes start, and excludes stop — the same half-open rule as range().

word = "Python"
print(word[0])       # P
print(word[-1])      # n
print(word[1:4])     # yth
print(word[:3])      # Pyt
print(word[3:])      # hon
print(word[::2])     # Pto
print(word[::-1])    # nohtyP   (a reversed copy)

Read word[1:4] as "characters from index 1 up to but not including index 4". Leaving out start means "from the beginning"; leaving out stop means "to the end". A negative step walks backwards, which is the idiomatic way to reverse text.

Indexing and slicing differ in how they react to being out of range. word[100] raises IndexError, while word[2:100] simply returns "thon": slice bounds are clamped, so a slice can never fail this way. That makes slices safe when the string length is unknown in advance.

Strings are immutable

You cannot change a character in place. Rebinding the name to a new string works because that creates a new object, but the old one is never modified. The same holds for every "modifying" method: strip(), replace() and friends return a new string and leave the original untouched.

name = "ada"
# name[0] = "A"        # TypeError: 'str' object does not support item assignment
name = "A" + name[1:]
print(name)            # Ada

greeting = "hello"
shouted = greeting.upper()
print(greeting, shouted)   # hello HELLO

This has one practical consequence worth learning early: the result must be used. A line that reads line.strip() on its own does the work and then throws it away. You need line = line.strip(). Almost everyone hits this bug once, and the traceback will not help, because nothing has failed — the program simply behaves as if the call were never made.

The methods you will actually use

Python has a lot of string methods. A small set covers almost all real work. strip() removes whitespace, or a given set of characters, from both ends, with lstrip() and rstrip() for one side. split() cuts a string into a list and join() glues a list back into a string. replace() swaps substrings. find() and index() locate a substring. count() counts occurrences. The case methods upper(), lower(), title() and casefold() change casing. startswith() and endswith() test beginnings and endings, and the is... family such as isdigit() and isalpha() classifies content.

raw = "  Grace Hopper  "
print(raw.strip())                  # 'Grace Hopper'
print(raw.strip().lower())          # 'grace hopper'

print("a,b,,c".split(","))          # ['a', 'b', '', 'c']
print("one  two   three".split())   # ['one', 'two', 'three']
print(" | ".join(["x", "y", "z"]))  # x | y | z

print("banana".replace("na", "NA", 1))  # baNAna
print("banana".count("an"))             # 2
print("report.txt".startswith("rep"))   # True
print("report.txt".endswith(".txt"))    # True

find() and index() both report a position, but they disagree about failure. find() returns -1 when the substring is missing; index() raises ValueError. Use find() when absence is normal, and index() when absence is a bug you want to hear about.

print("banana".find("na"))    # 2
print("banana".find("zz"))    # -1
print("x" in "banana")        # False

try:
    position = "banana".index("zz")
except ValueError:
    position = -1
print(position)               # -1
Watch out. if text.find("@") is a bug: a match at index 0 returns 0, which is falsy, so the check fails exactly when the substring sits at the very start. Compare with != -1, or use "@" in text. Be careful with isdigit() too — it accepts only decimal digits, so "-7".isdigit() and "4.2".isdigit() are both False. Parse with int() or float() when you actually need a number.
Tip. split() with no argument splits on runs of any whitespace and drops the empty pieces, which is exactly what you want for messy user input. split(" ") does not: it splits on single spaces and keeps the empties. Reach for the bare call first.

f-strings that line up

An f-string is a string literal prefixed with f in which braces hold expressions. Anything inside the braces is evaluated and inserted. A colon after the expression starts the format specification, which controls width, alignment and precision — the part that turns output into a readable report instead of a pile of digits.

name, score = "Ada", 0.9317
print(f"{name:>10}|")   #        Ada|
print(f"{name:<10}|")   # Ada       |
print(f"{name:^10}|")   #    Ada    |
print(f"{score:.2f}")   # 0.93
print(f"{score:.1%}")   # 93.2%
print(f"{42:05d}")      # 00042
print(f"{1234567:,}")   # 1,234,567

Read 10 as "ten columns total", > as right-aligned, < as left, ^ as centered, and the leading zero in 05d as "pad with zeros". The .2f means two decimal places, .1% means one percentage decimal, and , inserts thousands separators. Combinations are allowed: f"{price:>8.2f}" right-aligns a price in eight columns with two decimals, which makes a column of numbers easy to scan.

Two smaller habits pay off. Use !r to show the repr() of a value while debugging, so trailing spaces and newlines become visible: print(f"{line!r}"). And keep the expression inside the braces rather than gluing strings with +, because f-strings convert numbers for you and keep the sentence in one readable piece.

Iterating characters and building strings

Strings are iterable, so for hands you one character at a time. Wrap in enumerate() when you also need the position, and use a generator expression with sum(), any() or all() for quick questions about content.

for index, ch in enumerate("abc", start=1):
    print(index, ch)

vowels = sum(1 for ch in "education" if ch in "aeiou")
print(vowels)          # 5
print("abc".isalpha()) # True

To build a string from many pieces, collect the pieces in a list and call join() once. The alternative, total += piece inside a loop, copies the whole accumulated string on every pass; that is fine for a handful of pieces and genuinely slow for thousands. Both versions below produce the same text.

parts = []
for word in ["alpha", "beta", "gamma"]:
    parts.append(word.upper())
print(", ".join(parts))   # ALPHA, BETA, GAMMA

total = ""
for word in ["alpha", "beta", "gamma"]:
    total += word
print(total)              # alphabetagamma

Remember that join() accepts only strings: convert numbers with str() first, as in "".join(str(n) for n in range(5)), which gives "01234". When you need a separator only between items, join() beats appending the separator yourself, which tends to leave a stray comma at the end.

A short note on Unicode and encoding

A Python str is a sequence of Unicode code points, not bytes. Files, sockets and terminals carry bytes, so text is encoded going out and decoded coming in. UTF-8 is the dominant encoding and can represent every code point using between one and four bytes.

s = "café"
print(len(s))                            # 4 characters
print(len(s.encode("utf-8")))            # 5 bytes
print(s.encode("utf-8"))                 # b'caf\xc3\xa9'
print(b"caf\xc3\xa9".decode("utf-8"))    # café

len() counts code points, which is neither bytes nor visible glyphs: an e followed by a combining accent is two code points that look like a single character. Mojibake — the cafÃ© kind — means bytes were decoded with the wrong encoding. The working rule is simple: keep text as str inside the program, and encode only at the boundary where bytes are required.

Watch out. open() without encoding= uses the platform default, which differs between machines — UTF-8 on most Linux systems, a legacy code page on some Windows setups. The same file then reads correctly on one computer and raises UnicodeDecodeError or produces mojibake on another. Pass encoding="utf-8" explicitly every time; Chapter 9 builds on that habit.

Chapter 8 — Exceptions and Debugging

An exception is not a verdict on your ability. It is a message from the interpreter saying: at this line, with these values, this operation could not be completed. This chapter teaches you to read that message in seconds, handle the failures you can fix, let the rest surface with a useful traceback, and debug on purpose instead of by guesswork.

What a traceback tells you

A traceback is a list of frames, one per function call that was active when the error happened. Python prints them from the outermost call down to the innermost. That order is backwards for reading, so start at the bottom.

def average(values):
    return sum(values) / len(values)

print(average([]))

Traceback (most recent call last):
  File "stats.py", line 4, in <module>
    print(average([]))
  File "stats.py", line 2, in average
    return sum(values) / len(values)
ZeroDivisionError: division by zero

The last line gives the exception type and message: ZeroDivisionError: division by zero. That alone usually names the problem. The line above it is the deepest frame — the exact statement that failed, here sum(values) / len(values) inside average. From Python 3.11 onwards, caret markers under the expression point at the subexpression that broke, which is often more useful than the whole line.

The frames above the deepest one tell the story of how you got there. Read upward from the failure: average was called from line 4 of the module, with an empty list. So the real cause is not division at all — an empty list reached a function that assumes at least one value. The traceback gives you the failure site; your job is to trace the bad value back to where it was born.

Frames in library code are usually noise: if most of a traceback sits inside site-packages and one frame is yours, start there. Each frame gives you file, line number and function name, enough to jump straight to the spot.

try, except, else, finally

A try block marks code that might fail. Each except clause names the exception it handles. The else block runs only when no exception occurred, and finally runs no matter what — success, handled failure, or an exception still on its way out.

def parse_age(text):
    try:
        age = int(text)
    except ValueError:
        print(f"not a number: {text!r}")
        return None
    else:
        print("parsed cleanly")
        return age
    finally:
        print("parse_age finished")

print(parse_age("42"))
print(parse_age("forty-two"))

Keep as little as possible inside try. If the block contains code that cannot raise the exception you are handling, you widen the net until the handler catches something unrelated. else exists for exactly that: it keeps the success path outside the guarded region. finally is for cleanup that must happen — closing a handle, releasing a lock, deleting a temporary file — and it runs even when the function is returning.

Catch narrowly, not everything

An except clause matches the named class and its subclasses, so except Exception catches nearly everything while except ValueError catches only value errors. Name the exception you expect. When several are possible, use separate clauses ordered from specific to general, because only the first match runs.

def divide(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        return float("inf")
    except TypeError:
        return None

print(divide(6, 3))    # 2.0
print(divide(6, 0))    # inf
print(divide(6, "x"))  # None

Bind the exception with as exc when you need its message or attributes: except OSError as exc: print(exc.strerror). The name is deleted at the end of the except block, which stops a stale reference from keeping the traceback alive.

Watch out. A bare except: catches everything, including KeyboardInterrupt and SystemExit, so Ctrl+C stops working and the program cannot shut down cleanly. Worse is except Exception: pass, which swallows the error and leaves you with a wrong answer and no clue. If you must handle broadly, record the exception first — traceback.print_exc() or print(type(exc).__name__, exc) — and never discard it silently.

EAFP and LBYL

Two styles compete for the same job. LBYL, "look before you leap", checks first and acts second. EAFP, "it is easier to ask forgiveness than permission", acts and handles the failure. Python generally prefers EAFP, because a check can be invalidated between testing and acting: a file can be deleted, a key can be removed, a disk can fill up.

record = {"name": "Ada"}

# LBYL
if "name" in record:
    name = record["name"]
else:
    name = "unknown"

# EAFP
try:
    name = record["name"]
except KeyError:
    name = "unknown"

# simplest when the API offers it
name = record.get("name", "unknown")

All three are correct here. The third is best because a well-designed API already encodes the default. Use EAFP when failure is rare and the cost of a failed attempt is small; use LBYL when failure would be expensive or would leave something half-done. What matters is that both branches are honest — neither style is an excuse to skip error handling.

Raising, re-raising, and custom exceptions

raise reports a problem the current function cannot fix. Raise early, with a message that includes the offending value, and let a caller who knows more decide.

def set_percentage(value):
    if not 0 <= value <= 100:
        raise ValueError(f"percentage out of range: {value}")
    return value

print(set_percentage(80))

Inside an except block, a bare raise re-raises the current exception with its original traceback intact. That is the right move when you want to log, add context or clean up without pretending you handled the problem. If you raise a different exception instead, chain it with from exc so the original cause stays visible in the report.

class InventoryError(Exception):
    """Base class for inventory problems."""


class OutOfStock(InventoryError):
    def __init__(self, sku, wanted):
        super().__init__(f"{sku}: wanted {wanted}, none left")
        self.sku = sku
        self.wanted = wanted


def reserve(sku, count, stock):
    if stock <= 0:
        raise OutOfStock(sku, count)
    return stock - count

try:
    print(reserve("A-12", 3, 0))
except InventoryError as exc:
    print(exc.sku, exc.wanted)   # A-12 3
    print(exc)                   # A-12: wanted 3, none left

A custom class is worth writing when callers must tell your failures apart from everything else. Subclass an existing exception when yours is a kind of it, as in class ConfigError(ValueError), and keep one base class per package so one except catches the family.

Debugging on purpose: print, assert, breakpoint()

Debugging is evidence gathering, not guessing. Print the value that should be there and the value that is there, with !r so whitespace is visible, then compare. Print the type too: "5" and 5 look alike in output and behave nothing alike.

values = ["3", "4", "5"]
total = 0
for item in values:
    print(f"item={item!r} type={type(item).__name__}")
    total += int(item)
print(total)   # 12

Replace one entry with "x" and the printout becomes the evidence: the value is a str, and int() refuses it, so the failure is a parsing problem rather than an arithmetic one. Printing the type is what separates the two.

An assert states an invariant that must hold at that point. When it does not, Python raises AssertionError with your message, which turns a silent wrong result into a loud, located failure.

def mean(values):
    assert values, "mean() needs at least one value"
    total = sum(values)
    assert total >= 0, "total went negative"
    return total / len(values)

Assertions check the programmer's assumptions, not user input: they are stripped out under python -O, so never use one to validate outside data. Raise a real exception instead.

When printing is not enough, call breakpoint() and the program stops there in the built-in debugger. You can inspect any variable, step one line at a time, and see the exact state at the failure.

def total_price(prices, discount):
    subtotal = sum(prices)
    breakpoint()          # execution pauses here
    return subtotal * (1 - discount)

print(total_price([10, 20], 0.1))

# at the (Pdb) prompt
# l        list the surrounding source
# p prices print an expression
# n        next line (step over calls)
# s        step into a call
# c        continue to the end or the next breakpoint
# q        quit the debugger and the program

You can also start a whole script under the debugger with python -m pdb script.py, which helps when the failure happens before you thought to add a breakpoint.

Tip. Read errors calmly and in a fixed order: the last line for type and message, the deepest frame for the failing statement, then upward for the caller that supplied the bad value. Say the message out loud as a sentence — "division by zero, because the list was empty" — and the fix usually names itself.

Chapter 9 — Files and Directories

Sooner or later every useful program touches the disk: read a configuration file, append to a log, load a CSV export, walk a folder of images. This chapter covers opening files with an explicit encoding, using with so handles always close, streaming large files line by line, and building paths with pathlib so your code behaves the same on every operating system.

Opening files: modes and encoding

open() returns a file object. The mode string decides what you may do with it: "r" reads and is the default, "w" writes and truncates, "a" appends, "x" creates and fails if the file already exists. Add "b" for binary mode, which hands you bytes instead of str, and "+" when you need both reading and writing on one handle.

from pathlib import Path

path = Path("notes.txt")

with open(path, "r", encoding="utf-8") as handle:
    first_line = handle.readline()

with open(path, "rb") as handle:
    header = handle.read(4)

print(type(first_line).__name__)   # str
print(type(header).__name__)       # bytes

In text mode always pass encoding="utf-8". Without it Python uses the platform default, so a file written on one machine can fail to decode on another, or decode into garbled characters. Binary mode takes no encoding at all — you are handed raw bytes, and decoding becomes your decision.

Watch out. Opening with "w" erases the file's contents the moment open() returns, before you write a single byte, and there is no undo. Use "x" when the file must not already exist, "a" when you mean to add to it, and keep "w" for files you intend to rebuild from scratch.

The with statement

with guarantees the file is closed when the block ends, including when it ends because of an exception. Call open() inside a with and you never have to remember close(), and you cannot leak a handle by returning early.

with open("log.txt", "a", encoding="utf-8") as handle:
    handle.write("started\n")
# the handle is closed here, even if write() raised

with (
    open("source.txt", encoding="utf-8") as source,
    open("copy.txt", "w", encoding="utf-8") as target,
):
    target.write(source.read())

The parenthesised form with two files needs Python 3.10 or newer; on older versions use two nested with statements. The object that with manages is called a context manager: it defines __enter__ and __exit__, and __exit__ runs no matter how the block ends. That is why the same pattern also covers locks, database transactions and temporary directories.

For short files, Path.read_text() and Path.write_text() open, use and close in one call, and they accept encoding too: Path("notes.txt").read_text(encoding="utf-8"). They are convenient, but they read the whole file into memory, so they suit configuration and small data rather than logs.

Reading line by line

Iterating over the file object yields one line at a time, newline included, without loading the whole file. This is the pattern to use for logs, exports and anything whose size you do not control.

total = 0
with open("numbers.txt", encoding="utf-8") as handle:
    for line in handle:
        line = line.rstrip("\n")
        if not line:
            continue            # skip blank lines
        total += int(line)
print(total)

Text mode translates line endings for you: \r\n from a Windows file arrives as \n, which is why rstrip("\n") is enough. If you need the raw endings, pass newline="" to open() and that translation stops.

Watch out. handle.readlines() and handle.read() load the entire file into memory. On a two-gigabyte log they exhaust memory or push the machine into swap, and the program appears to hang before it dies. Iterate the handle instead, or read fixed-size chunks with handle.read(65536) when you need bytes.

readline() returns one line, readlines() returns a list of all of them, and iteration hands them over lazily. Prefer iteration unless you genuinely need random access to every line at once.

Writing and appending

write() does not add a newline for you, so include \n yourself. Pass newline="\n" to open() when writing if you want byte-identical output everywhere: it disables translation, so a file written on one system reads the same on every other.

from pathlib import Path

rows = ["alpha", "beta", "gamma"]

with open("out.txt", "w", encoding="utf-8", newline="\n") as handle:
    for row in rows:
        handle.write(row + "\n")

with open("out.txt", "a", encoding="utf-8", newline="\n") as handle:
    handle.write("delta\n")

text = Path("out.txt").read_text(encoding="utf-8")
print(text.splitlines())   # ['alpha', 'beta', 'gamma', 'delta']

splitlines() splits on every line-ending convention and drops the terminators, which makes comparisons easier than splitting on "\n". Flushing matters when another process reads the file while yours is still running: handle.flush() pushes buffered bytes out, and closing the handle flushes automatically.

pathlib for paths and directories

Build paths with the / operator instead of gluing strings. Path supplies the separator for the current system, collapses redundant slashes, and exposes named parts.

from pathlib import Path

project = Path.home() / "projects" / "demo"
project.mkdir(parents=True, exist_ok=True)

data = project / "data.txt"
data.write_text("hello\n", encoding="utf-8")

print(data.exists())                       # True
print(data.name, data.stem, data.suffix)   # data.txt data .txt
print(data.parent)                         # .../projects/demo
print(data.read_text(encoding="utf-8").strip())

mkdir(parents=True, exist_ok=True) creates missing parents and does not complain when the directory already exists, which is what you want in setup code. Beyond that, Path offers iterdir(), glob(), rglob(), rename(), unlink(), is_file() and is_dir(). Paths are objects, so they compare and print sensibly and pass straight into open().

os.listdir versus glob

os.listdir() returns bare names — no directory part, no filtering, directories included. glob returns full paths that match a pattern. With pathlib you rarely need either from os.

import os
from pathlib import Path

names = os.listdir(".")                      # names only, unfiltered
print(sorted(n for n in names if n.endswith(".txt")))

for path in Path(".").glob("*.txt"):         # paths, filtered
    print(path.name)

for path in Path(".").rglob("*.py"):         # recursive
    print(path.relative_to("."))

Neither call filters hidden entries, and neither guarantees an order, so sort the results before printing or comparing them. Use rglob() for recursive matches, or glob("**/*.py"), which means the same thing.

Tip. Prefer pathlib in new code. Path objects work on every platform, support / for joining, .parent and .with_suffix() for derivation, and pass directly to open(). Reach for os.path only when maintaining older code.

CSV files and separators

The csv module handles quoting, embedded commas and header rows, none of which string splitting gets right. Write with csv.writer or csv.DictWriter, and read with csv.reader or csv.DictReader.

import csv

with open("scores.csv", "w", encoding="utf-8", newline="") as handle:
    writer = csv.writer(handle)
    writer.writerow(["name", "score"])
    writer.writerow(["Ada", 93])
    writer.writerow(["Grace", 88])

with open("scores.csv", encoding="utf-8", newline="") as handle:
    for row in csv.DictReader(handle):
        print(row["name"], row["score"])
Watch out. Pass newline="" whenever you hand a file to csv. The module writes its own line terminators; with translation left on, Windows turns each one into a blank row between records. It is the most common CSV bug, and the fix is a single keyword argument.

Never hard-code a separator. Three of them bite: the path separator, the CSV delimiter, and the line ending. Join paths with / through Path rather than typing "\\" or "/", which assumes an operating system. Pass the delimiter to csv explicitly rather than assuming a comma — the same export from a spreadsheet can arrive semicolon-separated in one locale and tab-separated in another.

import csv

with open("export.csv", encoding="utf-8", newline="") as handle:
    sample = handle.read(2048)
    handle.seek(0)
    dialect = csv.Sniffer().sniff(sample, delimiters=",;\t|")
    for row in csv.DictReader(handle, dialect=dialect):
        print(row.get("name"), row.get("score"))

When the source is under your control, state the delimiter instead of guessing: csv.DictReader(handle, delimiter=";") is clearer than sniffing and far clearer than line.split(","). Sniffing is a fallback for files you did not produce.

Tip. Keep the encoding, newline and delimiter decisions in one small helper that opens the file. Then a change of format is a single edit rather than a search through the code.
